## 一、P0 级问题（不解决不敢给真实客户用）

### 1. 全项目零自动化测试
- `backend/pyproject.toml` 配了 pytest，但**仓库里没有任何 test 文件**（find 出来的全在 `.venv` 里）；前端无 vitest、无 playwright 配置。
- 后果：今天改 `face_selected_ids`，我只能写临时脚本手测，跑完就删；下次谁动 `gallery.py` / `detector.py` 没有回归网。
- **建议**：判定器是天然可测的（输入帧 → 输出判定结果，纯函数化程度高）。
  - 第一批必补：`FaceGallery.best_match`（含 filter_ids 语义）、`FaceDetector` 状态机（stranger/blacklist/verify 三条判定路径）、`EventRule` schema 校验、`alarms-since` 水位逻辑。
  - 主流程 E2E 用 Playwright 固化：登录 → 建事件 → 绑模型 → 启动任务 → 出告警 → 转人脸库。
  - 接 GitHub Actions：push 即跑 pytest + `npm run build` + lint。

### 2. `sys_log` 对每个请求全量落库，会无限涨
- `core/middleware.py:51` 的 `OperationLogMiddleware` 对**所有** `/api/v1/` 请求（含 GET）都写一行 `sys_log`。
- 监控台轮询频率：告警 3s、状态 5s、看板 30s。**单个开着的浏览器 tab ≈ 600+ 行/小时 ≈ 500 万行/年**。
- 后果：SQLite 文件膨胀、日志列表查询变慢、`sys_log` 最终变成噪声（真正想查的操作被埋掉）。
- **建议**（四步，任选组合）：
  1. GET / OPTIONS 不记（只记 POST/PUT/DELETE）；
  2. 高频轮询类接口按 path 采样，只记 1%；
  3. 加归档任务：保留 30 天，超期删或转冷存；
  4. 长线看，操作日志应该走文件（loguru）而非业务库。

### 3. 单进程 uvicorn + 无进程守护（已两次翻车）
- 后台任务被环境回收过两次，用户侧表现是 `Network Error` / `timeout`，只能人工重启。
- 现在靠 Bash `run_in_background` 托管，父进程退出即死。
- **建议**：
  - 最低限度：`start_platform.bat` 加 watchdog 循环（进程死了自动拉起）；
  - 正确做法：`docker-compose.yml`（backend + frontend-nginx + 可选 postgres）+ `restart: unless-stopped`。deploy/ 里已有 nginx 和构建脚本，补 compose 成本很低。

### 4. 人脸数据合规缺关键能力（PIPL 硬要求）
- 人脸 embedding 属于敏感个人信息，当前：无授权书上传、无保留期限、无"导出/删除个人数据"接口（被遗忘权）。
- 已知灰色地带：训练数据（WIDER FACE）研究用途声明，已记录在案。
- **建议**补齐四件套：
  1. 登记时上传《授权书》附件 + 授权有效期字段；
  2. 数据保留期限配置 + 到期自动清理任务；
  3. `POST /faces/{id}/export`（导出该人全部数据）、`DELETE` 真删除（含照片文件）；
  4. 关键操作（人脸库增删改、告警确认）写 append-only 审计表，防篡改。

### 5. 默认弱口令 + 密钥管理
- admin/admin123；JWT secret 位置需确认走环境变量。
- **建议**：首登强制改密；密钥全部走 env / 密钥管理服务，禁止入库。

## 二、P1 级问题（影响规模与稳定性）

### 6. 视频源只支持 RTSP / 本地文件
- 国内安防现场 90% 是 **GB28181 国标**，其次是 ONVIF；RTMP / HLS / FLV 也常见。
- **建议**：抽象 `VideoSource` 接口（当前 grabber 应该是紧耦合的），按优先级接：GB28181（SIP+invite）→ ONVIF → RTMP/HLS。这是"能进现场"的硬门槛。

### 7. 告警只有入库，无外发通道
- 现在告警存库 + 前端轮询，人必须盯屏幕。
- **建议**：插件化通知通道 —— 企业微信机器人 / 钉钉 / Webhook / 邮件 / 短信 / 声光。配"告警升级策略"（N 分钟未确认 → 通知上级）。

### 8. 告警无处置闭环
- 目前告警可"转样本 / 转人脸库"，但没有"确认 / 误报 / 已处理"状态流转、无处置人、无备注、无响应时长统计。
- **建议**：`alarms` 表加 `status(pending/confirmed/false_positive/ignored)` + `handler` + `handled_at` + `note`；告警中心加处置按钮和筛选；顺带能算"误报率"，这是客户最关心的指标。

### 9. 人脸库规模天花板
- `best_match` 是 O(N) 暴力扫 128 维矩阵。当前库 3 人；1 万人 → 128 万 float32 = 512MB 内存，且每张脸一次全量 matmul。
- **建议**：>500 人上向量索引（faiss / hnswlib，或迁 pgvector）。可先做"分组过滤 + 索引"二级结构，多数场景分组后数量不大。

### 10. 轮询架构浪费 + 与问题 2 叠加
- 监控台 3s/5s 轮询、看板 30s；既压数据库又制造日志噪声。
- **建议**：告警推送改 SSE 或 WebSocket（告警本就是事件驱动，天生适合推送）；退而求其次至少：① 页面不可见时暂停轮询（`document.visibilityState`）；② 已用 `since_ts` 增量，继续保持。

### 11. 无全局并发闸 / 背压
- 每个任务一个 `threading.Thread`，没有全局上限。8 路同时跑 + 每路 44–177ms/帧，CPU 打满时行为未知。
- **建议**：全局信号量（按 CPU 核数动态算上限）、任务优先级、显式的帧丢弃策略（当前是否有？需确认 grabber 在解码慢时是堆积还是丢帧——堆积会内存溢出）。

### 12. 模型无版本管理与回滚
- 有热替换（mtime+size），但没有版本记录/checksum/发布时间，也没有回滚。
- **建议**：`models` 表加 `version` / `sha256` / `published_at`；支持"回滚到上一版"；上线新模型前跑影子模式（并行推理、只记录不告警，观察 7 天再切换）。

### 13. SQLite 的单机天花板
- 单文件 + WAL，多人同时写会撞锁；告警量大、人脸库上万后会疼。
- **建议**：SQLAlchemy 已抽象，主要工作量在 alembic 迁移脚本 + 向量检索换 pgvector。建议做成"可切换"而非"默认切"，单机版保留 SQLite 降低部署门槛。

## 三、P2 级问题（体验与工程债）

### 14. 前端三个巨型单文件
- monitor 1,160 行、samples 1,134 行、events 1,093 行、train 963 行。
- **建议**：按职责拆组件。优先拆 monitor：`MonitorVideo` / `AlarmTimeline` / `MonitorControls` / `SnapshotDrawer`。events 表单也可拆 `FaceRuleForm` / `DivingRuleForm` 等，顺带解决问题 15。

### 15. 加一个规则字段要改三处
- schema（后端白名单）→ detector（读取）→ 前端表单，三处手工同步。今天加 `face_selected_ids` 就是走这套。
- **建议**：用 JSON Schema 驱动表单（pydantic 可直接生成），或抽一个 `rule_fields` 注册表，把"声明一处"做成可能。

### 16. 表单按模式的前置校验不完整
- diving / climbing / absence / identity 都有前置校验和友好提示，**face 四个模式没有**（如：黑名单模式但人脸库为空；record 模式 selected_ids 选空是否要提示）。
- **建议**：把已有的校验模式推广到 face 全模式，统一风格。

### 17. 无新手引导 / 空状态链路
- 新用户进来：无摄像头 → 无模型 → 无事件 → 无任务，四段链路，每页空状态只有"暂无数据"。
- **建议**：每页空状态给"下一步"动作按钮；做一个 4 步 onboarding 向导（接摄像头 → 选模型 → 建事件 → 开任务）。

### 18. 无全局错误边界
- 单个组件渲染异常会白屏，没有 `app.config.errorHandler` / ErrorBoundary。
- **建议**：加 `onErrorCaptured` + 兜底页，至少让用户能看到"出错了，刷新重试"而不是白屏。

### 19. 日志只进控制台，不落文件不轮转
- `core/logging.py` 用 loguru 但只配了 colorized console。
- **建议**：加 rotating file sink（按天+按大小），生产环境排查问题不能没有日志文件。

### 20. 无数据库 / 文件备份策略
- SQLite 单文件 + `uploads/` 图片，没有自动备份。
- **建议**：定时 `sqlite3 .backup` + uploads 打包，异地留存。

### 21. 无 i18n / 移动端适配
- 全中文硬编码；监控台是"值班大屏"场景但用的是桌面 admin 布局。
- **建议**（优先级低于以上）：监控台做深色大屏皮肤 + 自适应；手机端做"收告警 + 确认"精简页；若要出海再上 vue-i18n。

### 22. 阈值调优缺工具
- 0.363 是 P0 实测得出的，上线后误报/漏报只能手改 rule 再观察。
- **建议**：做"阈值实验台"——拿历史告警+样本，滑动阈值画 P/R 曲线，一键应用到事件。

### 23. 样本→训练→上线闭环仍靠手工
- to-sample 已支持，但"低置信度样本收集 → 标注 → 训练 → 评估 → 上线"是人在推。
- **建议**：主动学习闭环：低置信度自动进待标注池 → 训练 → mAP 与上一版对比 → 达标一键上线（配合问题 12 的影子模式）。

## 四、下一步方向（我的判断）

### 4.1 先明确一件事：这个产品现在处在哪个阶段？

它现在是一个**"AI 视觉算法验证平台"**——算法能跑、能出结果、能训练迭代。但正在往**"安防监控产品"**走。这两个阶段要的能力完全不同：

- 验证平台：客户要的是"算法准不准"→ 已基本达标。
- 安防产品：客户要的是"**我敢不敢让它 7×24 看着，出了事我能不能说清楚**"→ 目前不及格。

**所以下一步不该继续铺功能，该补"可信度"。** 每加一个新算法模式的边际价值，远低于把告警闭环、测试、部署这三件事做扎实。

### 4.2 三阶段路线

**阶段 1：可信度与可验收（1–2 个月）**
> 目标：能拿给一个真实客户试点，并且你敢签字。

- pytest 覆盖全部判定器 + Playwright 固化主流程（问题 1）
- 告警处置闭环：确认/误报/统计准确率（问题 8）
- 阈值实验台（问题 22）
- docker-compose 一键部署 + 进程守护（问题 3）
- sys_log 治理（问题 2）
- 人脸合规四件套（问题 4）
- 如目标客户在国内：GB28181 接入（问题 6）

**阶段 2：规模与稳定性（2–4 个月）**
> 目标：50+ 路、万人脸库、7×24 不重启。

- PostgreSQL + pgvector 迁移路径（问题 9、13）
- 全局并发闸 + 背压 + 帧丢弃策略（问题 11）
- SSE/WebSocket 替代轮询 + 页面不可见暂停（问题 10）
- 告警外发通道（企微/Webhook/短信）+ 升级策略（问题 7）
- 模型版本管理 + 回滚 + 影子模式（问题 12）
- 日志落文件轮转 + 定时备份（问题 19、20）

**阶段 3：产品化（4–6 个月）**
> 目标：能卖、能交付给多个客户。

- 多租户 / 项目数据隔离
- 大屏值班模式（深色皮肤）+ 移动端告警 App
- 报表与考核：告警响应时长、误报率趋势、值班绩效
- 主动学习闭环全自动（问题 23）
- 插件市场 / 第三方算法接入

### 4.3 如果只能做三件事

1. **pytest + Playwright** —— 没有测试网，后面每一次改动都在赌。
2. **告警处置闭环** —— 这是"演示"和"产品"的分界线，客户第一个问题就是"误报了怎么办"。
3. **docker-compose 部署** —— 已经翻车两次了，交付时不能再让人手动起进程。

### 4.4 一个需要你决策的岔路

**要不要现在迁 PostgreSQL？**

- 支持现在迁：向量检索、并发写、告警量增长都是硬需求，晚迁迁移成本更高。
- 支持晚迁：SQLite 部署零依赖，对"单机版卖给小客户"是优势；且当前还没到瓶颈。

我的倾向：**阶段 1 保持 SQLite，但阶段 1 期间就把 alembic 迁移脚本建起来**（哪怕只有一个 baseline），保证阶段 2 切换时不是从零开始。同时把"是否支持 PG"做成一个明确的部署选项而不是隐式假设。
