## A-2 ｜ 问题 2：`sys_log` 对每个请求全量落库

**现状证据**：`backend/src/core/middleware.py:51` `OperationLogMiddleware` 对所有 `/api/v1/` 请求（含 GET）写一行。监控台轮询 3s/5s/30s → 单个开着的 tab ≈ 500 万行/年。

**怎么改**：

## B-9 ｜ 问题 11：无全局并发闸 / 背压

**前置条件**：需要多路实测数据才能定阈值；但机制可以先建。

**怎么改**：

1. **全局信号量**：`runtime/manager.py` 加一个进程级 `threading.BoundedSemaphore(max_concurrent)`，`max_concurrent` 默认按 CPU 核数算（如 `min(4, cpu_count)`），可在配置里改。任务启动时 acquire，停止时 release。
2. **帧丢弃策略显式化**：确认 `grabber.py` 在解码慢于处理速度时的行为。**当前最需要排查的是：是丢帧还是堆积？堆积会内存溢出**。若为堆积，加一个有界队列（`queue.Queue(maxsize=2)`），满了就丢最新/最旧帧。
3. **优先级**：`AIVisionTask` 加 `priority` 字段，信号量竞争时高优先级任务先拿。
4. **背压指标**：`last_stats` 里记录"丢弃帧数"，前端任务列表展示——让用户看得见系统在丢帧而不是假装正常。

- **工作量**：中
- **风险**：中。改并发行为容易引入难以复现的问题，**必须在 A-1 测试网建好后做**
- **依赖**：**强依赖 A-1**；需要实测定阈值

## B-13 ｜ 问题 23：样本→训练→上线闭环手工

**前置条件**：依赖 B-9（并发/资源管理）和 B-11（评估工具）；且训练本身吃 GPU。

**怎么改**：

1. **待标注池**：worker 推理时对低置信度检测（`confidence` 在阈值附近一个区间，如 0.25~0.45）自动抓拍入"待标注池"（新增样本 `source=lowconf`）。**这是主动学习的标准做法**，成本低收益高。
2. **一键训练**：样本页选一批 → 直接建训练任务（已有 train_runner，接起来即可）。
3. **自动评估对比**：训练完成后自动算 mAP，与当前线上模型对比，达标提示"可上线"，不达标给出差距。
4. **上线即留痕**：上线时写模型版本记录（配合 B-14），可回滚。

- **工作量**：中到大
- **风险**：中（自动化流程出错会浪费训练时间）
- **依赖**：B-14（版本管理）先做，否则"上线"没有回滚点

## B-14 ｜ 问题 12：模型无版本管理与回滚

**前置条件**：DDL 变更安全（alembic + 补列已确认可用）。

**怎么改**：

1. **改 `models.py` 模型表** 加：`version`（自增或语义化）、`sha256`（文件校验）、`published_at`、`is_current`（当前线上版本标记）。加字段靠 `_ensure_columns` 自动迁移。
2. **上线流程**：上传新模型默认 `is_current=false`，点"设为线上"时才切换，并把上一个 `is_current` 置回。**天然获得回滚点**。
3. **回滚**：模型列表加"回滚到此版本"，实际是把该版本文件复制为当前生效文件（engine LRU 按 mtime+size 判新，**免重启热替换的机制已经现成**）。
4. **影子模式（可选，第二阶段）**：新模型并行推理只记录不告警，跑 N 天后出对比报告。**本机 8GB 无 GPU 跑不动双倍推理，此功能需在有 GPU 的部署环境验证**。
5. **前端** `frontend/src/views/ai_vision/models` 或 `train/index.vue`：版本列 + 上线/回滚按钮 + sha256 展示。

- **工作量**：中
- **风险**：低到中。主要是 `is_current` 的并发切换要加锁，避免两个请求同时切
- **依赖**：无（可独立做）；影子模式部分依赖 GPU 环境

## B-15 ｜ 问题 9：人脸库 O(N) 暴力扫

**前置条件**：当前库 3 人，无实际压力。但**超过 500 人前必须做**。

**怎么改**：

1. **第一阶段（不改架构，先扩容）**：`gallery.py` 的 `_ensure` 加载时按 group 分成两个矩阵，`best_match` 先按 group 取对应矩阵再算——避免混算浪费。顺带把 `_mat` 从 float32 确认（已是）。
2. **第二阶段（>1000 人）**：上向量索引，按依赖轻重三选一：
   - **faiss**（`faiss-cpu`，纯本地，无外部服务）——最适合当前架构，改动最小，`IndexFlatIP` 或 `IndexHNSWFlat`
   - **hnswlib**——更轻，API 更简单
   - **pgvector**——只有迁了 PG 才考虑
3. **改造点**：`best_match` 内部把 `self._mat[idx] @ vec` 换成索引 `search`，返回 top-k 再按 `filter_ids` 过滤。**注意 faiss 的 top-k 要先多取一些（如 k=50）再过滤**，否则 filter 会把正确结果滤掉后没有备选——这是最容易出 bug 的地方。
4. **配置开关**：人数小于阈值走暴力扫（确定性最好），大于阈值走索引。
5. **测试**：A-1 的 gallery 测试要补"索引路径与暴力路径结果一致"的用例。

- **工作量**：中
- **风险**：中。faiss 引入新依赖，且 top-k + filter 的交互容易出 subtle bug
- **依赖**：**A-1 测试网必须先建好**；无 PG 依赖（用 faiss-cpu）

## B-16 ｜ 问题 3：无进程守护 / 部署

**前置条件**：本环境无法验证容器；且你已有 `build_deploy_package.sh`。

**怎么改**（由轻到重）：

1. **最低限度（半小时）**：改 `start_platform.bat`，加 watchdog 循环——检测到后端/前端进程不在就重新拉起。解决"环境回收后不自愈"。
2. **中等（推荐）**：写 `docker-compose.yml`（backend + frontend 静态托管 + 可选 postgres）+ `restart: unless-stopped`。deploy/ 下已有 nginx 配置和构建脚本，拼起来成本不高。**这是交付时的正确形态**。
3. **写 `Dockerfile`**：backend 基于 `python:3.13-slim`（注意 opencv + onnxruntime 的系统依赖：`libgl1`、`libglib2.0-0`），前端用多阶段构建（node build → nginx serve）。
4. **健康检查**：compose 里加 `healthcheck` 打 `/api/v1/ai-vision/health`。
5. **注意**：模型文件（`assets/models/*.onnx`）和 `backend/uploads/` 不入库，要用 volume 挂载，不能打进镜像。

- **工作量**：中
- **风险**：低（新增部署文件，不动代码）
- **依赖**：本环境验证不了容器编排，需你在目标机器上验证；**watchdog 那步可以现在做并验证**

## C-19 ｜ 问题 15：加一个规则字段要改三处
- **怎么改（如果要做）**：pydantic 可直接 `model_json_schema()` 生成 JSON Schema，写一个 `SchemaForm` 组件（递归渲染 object/array/number/string/enum），事件表单的 rule 部分整体由 schema 驱动。加字段只需改 `schemas.py` 一处。
- **为什么不现在改**：大重构，现有表单有大量条件逻辑（`v-if` 按 detector 切换）和自定义组件（ROI 绘制、警戒线文本同步），schema 驱动会丢掉这些灵活性。性价比低于修具体问题。**折中方案**：先做一个 `rule_fields` 注册表，把"字段名+类型+默认值+校验"集中到一处，至少消除 schema 与 detector 读取处的重复。

## C-20 ｜ 问题 17：无新手引导 / 空状态
